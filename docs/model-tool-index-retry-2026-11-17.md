# 工具调用索引冲突未进入重试（2026-11-17）

## 结论

Chat 流解析器在同一个索引上看到不同工具调用 ID 时，原先返回普通 `fmt.Errorf`。`ClassifyFailure` 将其归为不可重试的 `unknown`，因此一次索引冲突就会终止整轮执行。已有的 `ToolCallError` 则被归为 `invalid_tool_call`，使用统一、有限的重试预算。

现在冲突返回携带索引、新调用及冲突 ID 的 `ToolCallError`，继续拒绝整个坏响应，通过既有重试机制重新请求。本次没有合并调用、推测匿名参数片段归属，也没有引入供应商特例、配置项或单独的重试循环。

## 实际证据与限制

会话 `a766dydsujih` 在 2026-11-17 14:41:13（Asia/Shanghai）开始的模型请求收到 HTTP 200，随后报 `model stream reused tool call index 0 ...`。前两轮共四个工具调用已完成，失败后的会话记录仍保留 9 条 History 和 6 条显示消息，并非会话数据整体丢失。

原始失败请求只保存了 trajectory 摘要，没有保存原始 SSE。因此无法从现有证据区分供应商真的重复索引、遗漏索引后被 Go 的整数零值代替，或其他具体帧布局问题。每个请求均新建 decoder，未发现解析状态跨请求复用的路径。

另外通过该会话配置的相同供应商和模型发送了一次独立合成请求：只声明两个无副作用的测试工具，不执行工具，也不发送原会话正文。捕获流中的两个调用分别使用索引 0、1；修复后重放解析通过。这证明该服务可以返回正常索引，不证明已重现原始异常流，也不证明真实业务会话已经恢复执行。

## 行为边界

- 索引冲突仍立即拒绝该次响应，坏批次中的工具调用不交给 Agent 执行。
- 重试保持已接受的请求内容不变，原先已完成的工具结果仍保留在历史中。
- 复用现有默认最多十次额外重试、取消与退避机制，不无限重试；持续返回冲突时仍会在预算耗尽后报错。
- 已观察到的用量和各次尝试继续记录；trajectory 额外保留结构化 `invalidToolCall`，便于区分索引冲突。
- 此修复不会自动重新执行已经结束的真实会话任务。
