# 上下文压缩边界提示优化（2026-11-17）

## 问题与决策

会话 `icl5eybdckon` 两次 CompressContext 均把结束引用选在一个包含两个工具调用的结果组中间。原校验返回同一条概括错误，把首消息、最近输入、近期消息和工具配对限制混在一起。模型第二次只修改了开始引用，结束位置未变，因此再次失败。

当时 ContextStatus 有 51 条消息，每页 40 条。索引 39 是第一个工具结果，索引 40 是同组最后一个结果；原第一页只列到索引 39，且没有给出可直接使用的完整范围。这种分页布局会增加选错结束引用的可能。

采用具体诊断和可执行边界建议，不自动改变压缩范围，不放宽保护规则，也不把失败显示成成功。

## 实现

- ContextStatus 在分页列表前输出最多两个最大安全范围，直接列出可用于调用的 `start_ref`、`end_ref` 和两端包含的索引。最近一次人类输入会把范围分开；首消息、至少八条近期消息及跨边界的完整工具组继续保留。
- 没有可压缩范围时，明确告诉模型继续任务、暂不压缩。
- CompressContext 分别报告引用不存在、范围倒置、保护消息和起止位置切断工具组等原因。
- 结束位置切断工具组时，若能在保护边界内补齐，直接给出最后一个工具结果的 `end_ref`，要求更新摘要以覆盖完整结果；不能补齐时，提示选择更早的完整组。
- 工具描述明确：两端引用都包含在范围内，结束引用必须包含整组工具结果；失败后按具体错误调整范围和摘要。

例如，原先概括的错误现在会变为：

```text
end_ref "m_39" splits a tool exchange; include all its results with end_ref="m_40" and update the summary to cover them
```

范围合法并不意味着任意摘要都会被接受。摘要仍须非空、最多 8000 字符，并实际减少上下文；持久化成功后才安装压缩视图，原文仍可检索。

## 验证

先增加双工具调用组的回归测试，原实现因错误中没有具体 `end_ref` 和可用修正而失败；修改后验证非法范围不会提交，按建议补齐后成功压缩且完整原文入档。

新增覆盖：

- 与真实记录相同的 51 条消息和分页边界，安全结束引用在索引 40、下一页才显示，但状态顶部可直接获取。
- 最近工具组跨越近期保护边界时，整个组保留，不给出越界建议。
- 缺失引用、倒置范围、首消息、最近人类输入、孤立工具结果和近期消息的具体诊断。
- 最近人类输入分隔的两个安全范围；不足八条消息时不显示可用范围。
- 非法压缩不改变历史和归档，修正后保留完整调用及结果。

测试日志位于 gitignored 的 `output/chat-tool-routing-20261117/context-memory-race.log`、`context-memory-final.log` 和 `context-engine-race.log`。此优化未执行原会话任务，也不证明模型一定会采纳建议；合法性仍由宿主校验。

实际结果：Agent 全包竞态检查通过（182 个顶层用例，含种子执行）；最终源码另通过 8 个压缩相关顶层测试。Engine 的 7 个压缩、归档持久化、提交失败回滚和侧会话边界顶层测试也通过竞态检查，覆盖三种模型协议的工具往返。没有修改 UI 颜色、存储格式、用户配置或原会话记录。
