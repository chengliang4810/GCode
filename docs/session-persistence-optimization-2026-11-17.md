# 大会话持久化优化（2026-11-17）

## 决策

当前采用紧凑 JSON 编码，以及提交成功后的尽力旧记录回收。这是在本次实际比较的方案中，兼顾延迟、内存分配与实现复杂度的选择，不代表对所有硬件和负载的全局最优证明。

- 会话记录与全局索引使用 `json.Marshal`，避免 `MarshalIndent` 对完整数据再次遍历、格式化与分配。
- 新记录仍通过文件同步、原子替换和目录同步落盘；全局索引仍在新记录之后同步提交。
- 只有索引提交成功后才回收已知前版本，仍先完整验证前版本 SHA-256。只省去垃圾删除后的额外目录同步，不修改通用 `storage.RemoveRoot`。
- 保存失败、事务顺序、调用方回滚和 Close 等待语义保持原有约束。R10 的全局过滤逻辑没有修改。

回收的取舍：断电可能使一个已删除但未同步的旧记录重新出现，形成无索引引用的孤立文件；不会把当前索引指向未完成的新记录。现有读取路径按索引定位记录，不扫描这些孤立文件。正常保存仍立即删除校验通过的旧记录。

## 比较范围

没有直接释放事务锁合并独立同步保存：现有调用方依赖同步错误进行回滚，提前返回或允许下个变更进入会破坏事务边界。现有后台补存已经按批次保存脏会话。

没有增加存储格式、依赖、缓存失效规则或用户配置项。JSON 字段、格式版本和读取方式不变；首次更新已有缩进记录时会自然生成新的内容哈希，不进行历史数据批量改写。

## 数据与方法

沿用 `nq7723skhoru` 主会话的只读私有副本，原始约 15.21 MiB。每份有 530 条消息、1126 条 History、1005 条 Context、629 条 ModelRequests、15 条 Runs、114 条 Changes。没有复制其 19 个子会话，也没有执行真实模型或工具。

1、10、20、50 份全部加载常驻，分别测量只保存一个、一次批量保存全部、多个 goroutine 同时请求并经过真实事务锁的保存。每种场景预热一次、测量五次，串行运行，使用真实临时 Store。计时前强制 GC 不计入，保存过程内 GC 计入。每个规模结束读取全部副本，验证 SHA-256、身份和记录数量。

方案比较先固定在 20 份：只紧凑化会话、同时紧凑化会话与索引、再省去旧垃圾删除目录同步；最终组合另完整复测所有规模。正文变化对照直接修改 History 和 Context 文本，保存后还逐字段比较完整消息、History、Context，避免仅改标题的偏差。

机器沿用基线：Intel i7-9750H（6 核 12 线程）、16 GiB 内存、macOS 14.8.7、Go 1.27.3、GOMAXPROCS=12。用户应用仍运行，结果是本机五次测量的中位数，不声明统计显著性或跨机器 SLA。

| 方案 | 只保存一个 | 批量保存 | 并发整批 |
| --- | ---: | ---: | ---: |
| 基线 | 0.353 | 5.141 | 7.117 |

| 再省去垃圾删除目录同步 | 0.262 | 3.891 | 5.306 |

### 最终完整复测（每种五次，中位秒）

| 份数 | 单个：基线 → 优化 | 批量：基线 → 优化 | 并发整批：基线 → 优化 | 并发耗时减少 |

| 50 | 0.464 → 0.352 | 13.235 → 10.003 | 23.660 → 17.150 | 27.5% |

### 分配与写入

| 份数与场景 | 总分配 MiB：基线 → 优化 | 会话记录写入 MiB：基线 → 优化 | worker P95 秒：基线 → 优化 |
| --- | ---: | ---: | ---: |
| 10 并发 | 1207.6 → 875.6 | 152.6 → 142.4 | 3.259 → 2.455 |
| 20 并发 | 2570.8 → 1933.7 | 305.2 → 284.9 | 6.877 → 5.225 |
| 50 并发 | 9573.0 → 5552.4 | 763.1 → 712.2 | 22.692 → 16.444 |

总分配量不是峰值常驻内存。每份优化后编码记录约 14.24 MiB；正文仍是主要体积，因此编码工作减少比磁盘字节减少更明显。

50 份并发仍需约 17 秒。当前整份快照重写与全局事务串行结构尚在，不把“每两秒触发补存”解释为“两秒内完成”。要进一步消除数据量线性增长，需要单独设计增量持久化与事务边界；本次结果不证明持续模型运行、前端流畅度或崩溃恢复的端到端表现。
