## 执行方式

1. 按 `reference/scenes.json` 的入口、页面、状态和交互逐项核对；缺失状态
   直接补实现，不把静态画面或近似组件标为完成。
2. 每项记录源码依据、字段来源、组件选择、触发步骤、实现图、行为检查和剩余差异。
3. 建立独立参考 harness，生产组件保持冻结，测试数据/窗口参数可控；
   原版图与实现图来源分别记录。用户数据不作为会被改写的验收 fixture。
4. 先统一布局、字体、基本组件和数据状态，再比较整窗及局部；小窗口、
   DPI、主题、悬停/焦点/错误/加载等条件单独覆盖。
5. 稳定阶段运行适当回归、vet/lint/race；源码冻结后再构建检查包，保存
   对应源码和二进制 hash，避免多架构混入不同修改。
6. Go诊断源与备份放在输出的 `_source/` 或独立nested module，不能仅依赖
   `.gitignore`；`go ./...` 仍会扫描忽略目录中的普通Go包。保持标准全量命令，
   不用过滤包列表掩盖污染；迁移保留原字节、哈希和失败日志。
   当前另以`output/go.mod`提供共享诊断module边界。`.9`首次标准全量命令发现
   未隔离证据副本而失败，原日志保留；新增边界不改既有证据路径/字节或2931项
   生产输入，仍使用标准根目录`go test ./...`，不靠过滤包列表绕过。
