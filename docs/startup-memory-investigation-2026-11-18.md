# 启动内存排查与修复（2026-11-18）

## 结论

模型目录在启动时先完整读取源 JSON，再建立元数据索引；首次启动/目录恢复/网络刷新还将已编码 JSON 交给 `MarshalIndent`，产生不必要的大缓冲。
修复使用 Go 标准库 `encoding/json/v2.UnmarshalRead` 流式解码缓存文件，复用 `storage.WriteJSONBytes` 原子写入已校验的源 JSON。
没有增加依赖、配置开关、强制 GC、内存上限或后台清理定时器。

保留目录结构和业务校验、离线种子、损坏恢复、刷新校验及三小时间隔。缓存读取错误仍返回错误；损坏内容恢复种子；非普通文件不会被替换。
流式解码检查整个输入，尾随 JSON/垃圾文本不能作为有效缓存接受。

## 测量方法与限制

当前用户进程初期 RSS 约 176 MiB，空闲几分钟后的物理内存足迹约 106 MiB。
RSS、物理内存足迹、Go HeapAlloc 和 Go Sys 是不同指标，不能相互替代或将共享页面全部计为业务数据。

Go 分阶段堆采样在独立的真实核心与 MyGo Tester 中执行，不读取用户会话和凭据。
仅在诊断测试进程中手动 GC，以观察存活对象；生产代码没有新增 GC 调用。
诊断探针未保留在生产或常规测试目录，源文件与 pprof 在 `output/startup-memory-20261118/` 留证。

原生采样串行启动修复前安装包与候选构建，均为 1320×880、空白独立资料目录，采样 2/5/10 秒后自行截图退出。
已有缓存场景只复制公开 models.dev 缓存（约 11 MB），不复制用户设置、供应商凭据或会话，并设置本地刷新时间避免外网请求。
未停止或操作用户原有进程；采样不是跨页面 E2E 或真实供应商验收。
原始数据：`output/startup-memory-20261118/native-results.json`，各场景的 `vmmap-*.txt`、`process.log` 和 `window.png`。
