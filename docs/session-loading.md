# 会话加载与持久化

## 数据边界

启动只读取 `engine.json` 中的配置、项目与会话摘要、记录哈希，以及执行请求身份等轻量元数据。
正文、模型历史、诊断记录和会话工具结果保存在会话所属数据根的独立记录中。
文件树与编辑器内容属于可重建状态，不再写入配置索引。

`Service.Snapshot(ctx)` 与 `Bootstrap(ctx)` 返回全局摘要；
`Snapshot(ctx, sessionIDs...)` 返回指定会话的详情。
`Subscribe(ctx, sessionIDs...)` 持有相同范围的正文引用，初始、增量及慢消费者重同步均遵守该范围。
投影先筛选详情再深拷贝，避免为未请求的会话分配正文副本。
远程适配器使用重复的 `sessionId` 查询参数表达范围，本机桌面直接调用强类型 Go 接口。

桌面范围来自中央会话与工作区可见的会话面板。
切换范围后取消旧订阅，使用代次拒绝旧后台结果，并清理离开范围的正文及展示缓存。
同一 revision 的快照仍可补齐刚请求的详情。
详情读取在核心锁外完成；并发请求同一记录共享读取，安装前重新检查记录版本和会话身份。

## 释放与执行

一次性快照完成后释放临时引用；持续订阅取消后释放其引用。
没有展示或后台引用的已保存空闲正文可以卸载，后续访问再读取。
命令完成或回滚后也检查释放，避免修改隐藏会话造成永久驻留。
执行中、后台子任务仍在工作、命名请求尚未退出、未提交修改、待发队列、
存活终端和活动目标均保护其需要的数据。
取消命名仅取消请求；后台请求完成记账后才释放其正文引用。
子任务完成时将父会话结果标记为 dirty 一并提交；
`TaskOutput` 按需重读已释放的子会话，提取结果后重新释放。
异步 hook 写入待发队列之前也必须加载所属会话，防止遗漏落盘或覆盖原历史。

执行请求 ID、状态及耗时等元数据持续保留在核心和索引中，
保证正文释放及重启后同一已接受请求不会再次执行或再次创建工作树。
会话正文卸载不会取消正在执行的任务，远程客户端断开也不会取消宿主任务。
重启读取时将失去执行者的运行状态归一为中断，打开正文时恢复工具和目标状态，
不会重新执行已发生的副作用。

## 定向提交

会话内容变更显式标记 dirty；保存只编码已变更的会话。
会话重排、分组、子会话及恢复修正也必须标记相应会话。
保存顺序为：

1. 写入新的会话记录。
2. 原子提交引用新记录的配置索引。
3. 校验并清理本次提交已知的旧记录。

索引提交失败保留先前有效记录及 dirty 状态；不以删除旧记录来腾空间。
清理只检查已知 predecessor，使用流式校验，不扫描目录或完整解码历史记录。
不删除无法证明属于当前提交的未知文件。
分组删除、会话重排必须提交全部受影响会话，任一记录写入失败就回滚整个命令。
独立历史盘离线时，其他盘仍可提交；离线会话的索引摘要和执行状态保留已提交版本，
不能引用旧正文却提前发布尚未保存的新摘要。

## 全局用量

`ApplicationUsageService.ReadApplicationUsage` 在用户打开统计时读取全局用量。
已驻留会话直接提取元数据，其余会话逐个读取并按不可变记录哈希缓存精简结果。
统计结果保留消息/执行身份、日期、模型、token、工具数和耗时，不保留消息正文。
fork 去重与统计口径沿用同一算法，不能用当前打开的会话代替全局统计。

## 2026-11-05 性能证据

证据保存在 `output/mac-resource-20261105/`。
旧版为安装程序 revision `828574c4d4e17f0679374394c8ebfef1ba087374`；
持久化基准使用当前 checkout 的原始 HEAD 源码作为修改前实现，
双方使用相同 Go 1.27.3 工具链和 fixture。

100 会话、每会话三份 32 KiB 正文、每轮只改一个会话的保存基准，
5 次结果中位数如下：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 分配字节/次 | 22,462,286 B | 476,522 B |
| 分配次数/次 | 830 | 336 |
| 耗时/次 | 177.17 ms | 85.41 ms |

分配字节减少约 97.9%。耗时受文件系统和系统负载影响较大，
该组样本未给出 benchstat 显著性结论，不能作为稳定的提速承诺。
可用 `persistence-benchmark/reproduce_benchmark.py` 重现，
原始样本为 `before-fixed.txt`、`after-fixed.txt`。

真实可见原生窗口的静态对照使用独立 profile、13 个会话、
每会话 128 条消息、5462 个工作区文件，单次运行 40 秒：

| 指标 | 修改前 | 首次修改后 | 最终应用包复核 |
| --- | ---: | ---: | ---: |
| 稳态 RSS 中位数 | 199.05 MiB | 157.18 MiB | 159.73 MiB |
| 16 秒 physical footprint | 143.2 MiB | 109.8 MiB | 110.6 MiB |
| 40 秒 physical footprint | 92.6 MiB | 71.6 MiB | 70.9 MiB |
| 稳态平均 CPU | 0.079% | 0.077% | 0.510% |
| 启动后配置索引 | 2,040,474 B | 23,226 B | 23,244 B |

RSS 与 physical footprint 是不同指标；CPU 100% 对应一个逻辑核心。
最终应用包复核在全仓测试和原生验收结束后，重新复制相同的合成数据到私有 profile，
使用包内可执行文件启动真实可见窗口，原始结果为 `after-final-measurement.json`。
对照旧样本，RSS 降低约 19.8%，40 秒 footprint 降低约 23.4%。
这是短时静态合成负载，空闲 CPU 在本轮样本中约 0.08–0.51%，
最终包的该次 CPU 样本高于旧样本，不据此宣称空闲 CPU 改善或回归，
不能与现场 6–7 个真实任务工作时约 24–31% 的 CPU 直接比较。
不据此宣称内存泄漏已证实或已消除，也不推断真实供应商多任务负载的 CPU 降幅。
原始采样、窗口截图及测量脚本位于 `native-comparison/`。
